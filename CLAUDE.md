# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project purpose

Crypts and Commits ("CAC") is a Coding Assistant Continuity Framework. It uses a tabletop-gaming metaphor to describe collaboration between a developer and an AI coding assistant: the developer acts as the Game Master, establishing context, making decisions, and retaining final authority over the session. Use "CAC", not "C&C", as the project's abbreviation — it aligns with the "Coding Assistant Continuity" subtitle and avoids reading as a direct D&D reference.

The framework's own CLI (`cac`) is meant to be driven by the coding assistant, not just the developer — it is the mechanism by which an agent records project context and tracks its own work. This repository dogfoods that idea: its own `.sourcebook` (see below) is live — a populated world summary, lore, regions, bosses, rumors, and campaign/encounter history — and is the actual source of truth for project context and in-flight work, not a placeholder. Before starting any nontrivial work in this repository, use the `world-manager` skill to prime context (world summary, applicable lore, relevant region) and the `campaign-manager` skill to check for an open encounter covering the task; if none exists, ask the user whether to create one before proceeding. Use the `world-planner` skill for goal (boss) planning, roadmap capture, readiness and dependency assessment, and triaging integrated rumors; use `campaign-manager` for explicit tactical selection of goals into campaigns and for encounter execution. Branch procedure follows the installed Branching Guide (`docs_get("branching-guide")` / `cac docs get branching-guide`), with the workflow guide (`docs_get("workflow")`) as the procedural authority — don't duplicate either here. Existing encounter review/open/completion approvals are unchanged. The longer-term goal is using the same framework to drive AI-assisted work on *other* projects.

## Guardrail: `.sourcebook/` is MCP/CLI-only

Once a project has been bootstrapped, its `.sourcebook/` directory is managed exclusively through the `crypts-and-commits` MCP server's tools (`world_*`, `lore_*`, `region_*`, `boss_*`, `campaign_*`, `encounter_*`, `rumor_*`, `prime_*`, `index_*`, `docs_*` — one module per domain in `mcp/`), falling back to the equivalent `cac` CLI commands (`cac world`, `cac lore`, `cac region`, `cac boss`, `cac campaign`, `cac encounter`, `cac rumor`, `cac prime`, `cac index`, `cac docs`) only when the MCP server isn't available for a session — never by creating, reading, editing, moving, or deleting files under `.sourcebook/` directly, whether with the `Edit`/`Write`/`Read` tools or via `Bash` (`rm`, `mv`, `sed -i`, `cat`, shell redirection, etc.). The long-term goal is for the coding assistant to have **no awareness of the `.sourcebook` directory's existence at all**; the MCP server now covers every command except `bootstrap` and `index rebuild`, both permanently CLI-only developer maintenance operations (see the `cli-mcp-parity` region lore, which keeps that property enforced going forward), and is the primary interaction layer today, not a future placeholder.

`Edit(.sourcebook/**)` is denied in `.claude/settings.json` — and, per Claude Code's permission-rule semantics, `Edit(path)` rules cover all file-editing tools including `Write`, so this single rule already blocks both; a separate `Write(.sourcebook/**)` entry would be accepted but silently unenforced (only `Edit`/`Read` path rules are matched), so don't add one. `Read` is deliberately **not** blocked either: skill instructions should still prefer the MCP `get`/`list` tools (or their `cac ... get`/`list`/etc. CLI-fallback forms) over reading files directly, but nothing yet technically prevents a direct `Read`. Treat the MCP/CLI-only rule itself as binding even where it isn't (yet) fully technically enforced.

For Codex, `cac bootstrap init` also deploys a project-local `.codex` `PreToolUse` hook that denies `apply_patch` file-operation targets inside managed `.sourcebook/` paths. It does not filter shell calls, nor ordinary-file patch content that merely mentions managed paths. The hook is a narrow guardrail, not a sandbox boundary, and its narrowness grants no bypass: the MCP/CLI-only rule above stays binding, and the `crypts-and-commits` MCP tools and `cac` CLI remain the approved sourcebook interfaces. Newly deployed project hooks require the developer to review and trust them through Codex's `/hooks` workflow before they run.

`cac bootstrap init` is invoked by the **developer only** — the coding assistant must never run it itself, even to fix a missing `.sourcebook`. If `.sourcebook` is missing, ask the user to bootstrap the project. The same applies to `cac index rebuild`: if the search index is reported stale or missing, ask the developer to rebuild it.

This restriction is about `.sourcebook/` *content*, not the `cac` source code itself — freely edit `packages/crypts-and-commits/src/cac/**` and its tests as normal.

`cac bootstrap init` provisions (creates, or merges into an existing) `.claude/settings.json` with this same `.sourcebook/**` Edit deny rule, an `allow` entry for the MCP server, and a matching `enabledMcpjsonServers` entry, for whatever project it bootstraps — the guardrail no longer has to be set up by hand as it was in this repo before this was implemented.

## Repository layout

This is a [PDM workspace](https://pdm-project.org/en/latest/usage/monorepo/) (`[tool.pdm.workspace]` in the root `pyproject.toml`) containing independent packages:

- `packages/crypts-and-commits` — the core framework: the `cac` Python package and its `cac` console script.
- `packages/demo-api` — a demonstration API used for development testing within the project (not a distributable library — `distribution = false`).
- `packages/demo-ui` — a demonstration Node.js UI exercising the demo API. *(Not yet added.)*

- In this workspace, `cac` is only on `PATH` via `pdm run cac ...` (the package is an editable install inside the workspace `.venv`, not a global install). This is a wrinkle of this repo's own dev setup — skill content (see below) invokes `cac` generically and should not encode `pdm run`.

## Architecture: the `cac` package

`packages/crypts-and-commits/src/cac/` is split into three subpackages, with a strict rule: **CLI modules are thin wrappers only — all real logic lives in `core`.**

- `core/` — domain logic, one module per concept (`world.py`, `lore.py`, `region.py`, `boss.py`, `campaign.py`, `encounter.py`, `rumor.py`, `prime.py`, `docs.py`), plus supporting domain modules and shared infrastructure:
  - `boss_candidates.py` — read-only boss eligibility and blocker explanations (`boss_candidates`); `boss_provenance.py` — validated, immutable roadmap-adoption snapshots for `boss_record`.
  - `campaign_bosses.py` — canonical campaign `bosses` membership (with read-only legacy scalar `boss` support); `coupling.py` — boss/campaign ownership, promotion (`boss_assign_campaign`), and the guarded campaign-lifecycle coupling that updates linked bosses' frontmatter (never their bodies).
  - `references.py` — numbered-name inventories and short-reference resolution (`bNNN`, `cNNN`, `rNNN`, `cNNN/eNNN`; exact canonical names win). Core resolves references but never allocates numbers — skills do.
  - `search_index.py` / `index_snapshot.py` — the derived full-text index and its content-based freshness evidence (never file times); `recovery.py` — scoped exception recovery for managed records and their index rows.
  - `budget.py` — the shared response budget, `paginate` cursor paging, and `fit_response`/body continuation used by every `list`/`get`.
  - `config.py` — all directory/file names, regex patterns, and status enums in one place.
  - `paths.py` — resolves the `.sourcebook` directory relative to a project root.
  - `frontmatter_utils.py` — shared helpers (`write_post`, `toggle_list_attribute`) for reading/writing YAML-frontmatter markdown via `python-frontmatter`; `git_utils.py` resolves `git user.name` for `created_by`/`updated_by`.
  - `templates/` — packaged, non-Python template files loaded via `importlib.resources` (critical: this is what makes templates ship inside the built wheel). Templates are grouped into subpackages by purpose: `templates/sourcebook/` holds the `.md` templates for the domain objects below; `templates/skills/{claude,codex}/{world_manager,world_planner,campaign_manager}/` holds the packaged agent-skill flavors deployed by `cac bootstrap init` (see "Agent skills" below); `templates/codex/` holds the Codex `PreToolUse` sourcebook-guard hook script deployed alongside the guardrail described above; `templates/docs/` holds the registered guides served by `docs_get`/`cac docs get`: `workflow.md` (Workflow Reference Guide — domain model, lifecycles/guards and skill procedure) and `tool-reference.md` (exact MCP/CLI contracts), a paired source of truth (see the `workflow-doc-source-of-truth` region lore), plus `branching-guide.md` (worked Git examples for the planning/assignment/execution branch workflow) and `migration-guide.md` (upgrades, workflow adoption and schema migration).
  - `bootstrap.py` — creates the `.sourcebook` directory and seeds `world.md`; `skills.py` deploys the packaged skills.
- `cli/` — one Typer module per `core` module, registered as a sub-`Typer` app in `cli/app.py` (two-tier help: `cac -h` lists modules, `cac <module> -h` lists that module's commands). `cli/common.py` holds shared helpers (`edit_markdown` — opens `$EDITOR` with a `.txt` extension even though the underlying file is `.md`; `fail` — prints and exits non-zero). Every `get` command prints its body via `console.print(body, markup=False)` — `rich.Console` defaults to `markup=True`, which silently strips bracketed text (e.g. `[tool.pdm.workspace]`) from anything rendered without that flag; any new command that prints stored content should do the same.
- `mcp/` — the MCP server exposing `.sourcebook` operations to agents: one module per domain (`world.py`, `lore.py`, `region.py`, `boss.py`, `campaign.py`, `encounter.py`, `rumor.py`, `prime.py`, `index.py`, `docs.py`), each a thin `@mcp.tool()`-decorated wrapper calling straight into `core/`, wired together in `server.py` via `_TOOL_MODULES`. This is now the primary interaction layer for `.sourcebook` — the CLI (above) is retained as a fallback for when the MCP server isn't available for a session. `bootstrap` and `index rebuild` are the two commands intentionally never exposed here (developer-only, see the guardrail above and `cli-mcp-parity`).

Tests under `packages/crypts-and-commits/tests/` mirror the `src/cac/` package structure (one test module per source module, split into `core/`, `cli/`, and `mcp/`).

## The sourcebook domain model

Bootstrapping a project (`cac bootstrap init`) creates a `.sourcebook/` directory in the project root holding these object types, all stored as markdown files with YAML frontmatter:

- **`world.md`** (singleton) — summary of the project's goals/purpose. Used to build context before applying world-level lore. Tracks `assigned_lore`, plus the `merge_target_branch` and `planning_branch` settings the skills use for the branch workflow (endpoints themselves stay branch-agnostic).
- **`lore/<name>.md`** — a standard, convention, or best practice used to review encounters before work begins. Lore assigned to the world is global (applies to every encounter); otherwise it only applies when assigned to a region the encounter takes place in. Tracks `enabled`, `assigned_to_world`, `assigned_regions`.
- **`region/<name>.md`** — a path within the repository needing its own documentation and lore (e.g. "frontend" vs. "backend" in a web app). Has a `path` attribute (not validated against the filesystem — regions may be aspirational) and tracks `assigned_lore`.
- **`bosses/<name>.md`** — a project goal that can be captured and refined before any campaign commits to it. Has a `status`: `proposed` → `available` (readiness recorded) → `vanquished` (only by completing its owning campaign), or `withdrawn` (unassigned only; reactivatable to `proposed`). Tracks `depends_on` prerequisite bosses (graph-validated), a scalar `campaign` owner, optional roadmap `provenance` (via `boss_record`, including historical completions), and an `archived` flag that moves the record under `archive/bosses/`. `boss_candidates` explains eligibility and blockers. A boss's design freezes once it is linked to a campaign or vanquished.
- **`campaigns/<name>.md`** — a long-running initiative, analogous to a Jira "Epic" (e.g. "Create the MVP"), expected to span many encounters before completion. Has a `status`: `draft`, `open`, `paused`, `completed`, `abandoned` (at most one `open` per checkout; `campaign_reactivate` reopens an unarchived `completed` campaign for pre-merge review fixes). Tracks a `bosses` list of zero, one or many selected goals, editable only while `draft`; complete/abandon/reactivate/archive update the linked bosses' frontmatter.
- **`rumors/<name>.md`** — a standalone backlog note ("we think X should be done") that can come from anywhere and be captured on any branch, with a required `summary` and free-text `origin`. Has a `status`: `open` → `promoted` (linked to an unassigned proposed/available boss, recorded only on the rumor — the boss is never written, and many rumors may share one) or `dismissed` (reason required); `reopen` returns either to `open`, and transition messages are kept in `history`. Only `open` rumors are editable. Promoted or dismissed rumors can be archived under `archive/rumors/`; there is no delete. Number collisions across branches are fixed on the `planning_branch` with `rumor_renumber`, which accepts open or dismissed rumors only — promoted numbers are settled. Rumors never affect bosses, candidates or campaign lifecycle and are not part of prime.
- **`encounters/<campaign>/<name>.md`** — a concrete unit of work within a campaign, of a fixed `kind`: `scripted` (default; a plan the agent is expected to execute, with fixed body sections `Requirements`, `Rationale`, `Plan`, `Verification`) or `unscripted` (a record of already-done work, with only `Requirements`/`Rationale`). Has a code-enforced `status` lifecycle: `draft` (only status where those sections may be replaced) → `reviewed` (once world/region lore checks pass, via `cac encounter review`, which locks the sections) → `open` (once the user approves and every direct dependency is completed, via `cac encounter open`) → `completed` (once work and verification finish and the user confirms, via `cac encounter complete`); `abandoned` is reachable from `draft`, `reviewed`, or `open` (via `cac encounter abandon`) but not from `completed`. Also has a `regions` list (an encounter may apply to one or more regions' lore; assignment is recorded only on the encounter, not back on the region) and a `depends_on` list of direct prerequisite encounter names within the same campaign.

Bosses, campaigns, encounters and rumors use numbered names (`b001-slug`, `c001-slug`, `e001-slug`, `r001-slug`, encounters numbered per campaign), and every existing-record input accepts short references (`bNNN`, `cNNN`, `rNNN`, `cNNN/eNNN`, or bare `eNNN` within the campaign context); unnumbered legacy names remain valid. Numbers are allocated by the skills (numeric max + 1 over the complete archive-inclusive inventory plus known campaign branch reservations), never by core. The recommended branch workflow — boss planning on the `planning_branch`, goal selection registered on a `cNNN-slug-assignment` branch, execution on the matching `cNNN-slug` branch, integration into the `merge_target_branch` — is skill guidance, not endpoint behavior; see `docs_get("branching-guide")` and the workflow guide.

Cross-object linking always lives on the "target" object's `core` module (e.g. `world.py` owns `assign_lore`/`unassign_lore`, `region.py` owns its own `assign_lore`/`unassign_lore`), while the corresponding CLI commands live under the "source" object being assigned (e.g. `cac lore assign-world`, `cac lore assign-region`, `cac encounter assign-region`).

Known limitation: deleting a lore/region/campaign entry does not cascade-clean stale references left in objects that were assigned to it.

## Agent skills

Two functionally-equivalent sets of three skills wrap the `crypts-and-commits` MCP server (falling back to the CLI when it's unavailable) so an agent session can drive `.sourcebook` content without ever touching it directly, per the guardrail above: Claude Code originals under `.claude/skills/`, and a Codex-native mirror under `.agents/skills/` (referencing the same MCP tools by their bare registered names, since Codex's MCP invocation surface doesn't share Claude Code's `mcp__crypts-and-commits__`-prefixed form; see `AGENTS.md`).

- **`world-manager`** — the static world-building context and disclosure ladder: world/lore/region tools and priming. Never calls `bootstrap` (developer-only, see the guardrail section, and intentionally not exposed over MCP at all).
- **`world-planner`** — goal planning before any campaign commits: boss capture/refinement, roadmap adoption, readiness and dependency assessment, integrated rumor triage (renumbering, promotion to bosses, dismissal, archival), and planning-side archival.
- **`campaign-manager`** — tactical commitment and execution: selecting goals into campaigns, campaign/encounter tools, rumor capture, the independent lore-review gate before an encounter moves `draft` → `reviewed` → `open`, and the verification/confirmation step before `open` → `completed`.

`cac bootstrap init` packages both flavors and deploys them into a target project's `.claude/skills/`/`.agents/skills/` (via `core/skills.py::deploy_skills`, backed by the `templates/skills/{claude,codex}/` files above). Unlike `world.md`'s create-if-missing semantics, every deployed skill file is overwritten unconditionally on each run, since skill content is framework-owned rather than user-editable data — a newer `cac` release must always be able to propagate an update to an already-bootstrapped project, at the cost of clobbering any local hand-edit to a deployed copy.

This repo's own `.claude/skills/` and `.agents/skills/` are **deployed artifacts, not source** — never edited directly, no matter how small the change. All skill content changes are made only in the packaged templates, `templates/skills/{claude,codex}/<name>/SKILL.md`; the developer then redeploys them into this repo the same way any bootstrapped project would, by running `cac bootstrap init` (never the coding assistant, per the guardrail above). See the `skills-authored-only-in-templates` region lore. This is a maturing of the dogfooding described at the top of this file, not an end to it: this repo no longer treats its own deployed copies as a second, hand-edited source of truth alongside the templates — the templates are now the only one, exactly as they are for every other project `cac bootstrap init` targets. A skill procedure change (not just wording) must also be reflected in the owning packaged doc in the same change — `templates/docs/workflow.md` for procedure, lifecycles and guards, `templates/docs/tool-reference.md` for tool/command contracts — see `workflow-doc-source-of-truth`.
