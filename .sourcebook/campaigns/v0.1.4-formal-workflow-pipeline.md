Establish a formal workflow document that lays out the entire structure of the `.sourcebook` domain model — world, lore, region, campaign, encounter — including the status-flow lifecycle for every content entity that has one (lore's enabled/disabled, campaign's draft/open/paused/completed/abandoned, encounter's draft/reviewed/open/completed/abandoned). This document becomes the single source of truth for how the domain behaves, independent of any one assistant's implementation.

The immediate motivation: today, `world-manager`/`campaign-manager` exist as two parallel skill trees (Claude Code under `.claude/skills/`, Codex under `.agents/skills/`) that are supposed to be functionally equivalent, but in practice one (Claude) is the de facto "primary" and the other is manually forked from it, drifting whenever the primary changes without a corresponding hand-edit. A shared workflow document lets each implementation-specific skill be authored *against* a common spec instead of against each other — so adding a third assistant flavor, or fixing a behavioral gap, means updating the spec once and re-deriving each implementation, rather than picking a new primary or re-forking.

Also needs to close gaps observed in actual `campaign-manager` usage that a clearer spec should help prevent:

- Region assignment is frequently skipped when creating/reviewing encounters — `encounter_assign_region` doesn't reliably get called even when an encounter clearly applies to a documented region.
- The required user confirmation before spawning the reviewer subagent (draft → reviewed gate, step 1 of the Encounter Lifecycle review process) is occasionally bypassed — the subagent gets launched without first stopping to get explicit approval.
