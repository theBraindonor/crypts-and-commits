## Requirements

- Add an `archived` column to the search index's FTS5 table (`sourcebook_fts`), populated `True`/`False` per row, so archived-ness becomes queryable index data rather than something only inferable from which directory a file happens to live in.
- `search()` (core) / `cac index search` (CLI) / `index_search` (MCP) gain an `include_archived: bool = False` parameter. Default (`False`): only live (non-archived) content is returned - the exclude-by-default behavior this encounter exists to deliver. `True`: live and archived content are both returned, undifferentiated in ranking, each hit carrying its own `archived` value. No third "archived-only" mode - a binary include/exclude toggle only, per explicit GM decision.
- `SearchHit` (core) gains an `archived: bool` field, populated from the new column. The MCP `index_search` hit dict and the CLI's printed result line both surface it: the CLI appends an `(archived)` marker to a hit's line only when `hit.archived` is true, so mixed live+archived result pages aren't ambiguous.
- `index_status`/`cac index status`/`index_counts()` are **unchanged** - counts stay grouped by `object_type` only, including archived rows in the total, with no live/archived split. Explicit GM decision: don't surface a breakdown nobody asked for; the asymmetry (status counts include archived, search excludes them by default) must be documented, not hidden.
- The `archived` flag must be set correctly by **all three** paths that populate the index, not just one:
  1. **Incremental sync at archive time** - `campaign_core.archive_campaign`/`encounter_core.archive_encounters` (from the prior encounter) already call `frontmatter_utils.write_post(root, new_archive_path, post)` for the moved file, unchanged by this encounter. `_classify()` must be extended to also recognize `.sourcebook/archive/campaigns/<name>.md` and `.sourcebook/archive/encounters/<campaign>/<name>.md`, mapping them to the **same** `(object_type, campaign, name)` identity as their live counterpart (rows are keyed by identity, not path) plus `archived=True`. Since `sync_write` already does DELETE-then-INSERT keyed on that identity, this makes the existing `write_post` call at archive time automatically flip the row's `archived` value to `True` with **zero changes** to `core/campaign.py` or `core/encounter.py`.
  2. **`rebuild_index`** - `_reindex_campaigns`/`_reindex_encounters` (already archive-aware from the prior encounter, scanning both live and archived directories) must tag rows from the live list `archived=False` and rows from the archived list `archived=True`.
  3. **`sync_delete`** - must keep working correctly once `_classify()` recognizes archive paths too: this is a bonus correctness fix, since today `campaign_delete`/`encounter_delete` on an *already-archived* item (reachable via the read-fallback added in the prior encounter) calls `delete_post` on the archive-location path, which `_classify()` currently doesn't recognize, silently orphaning that row in the index forever. Recognizing archive paths in `_classify()` fixes this as a side effect, not a separately-scoped change.
- Schema-change consequence, to be documented plainly (not hidden as a surprise): adding a column to an FTS5 table is not something `CREATE VIRTUAL TABLE IF NOT EXISTS` retroactively applies to an already-existing `.sourcebook/.index/sourcebook.db` built under the old 6-column schema. Any such pre-existing index must be rebuilt via `cac index rebuild` before further incremental syncs or searches work correctly - `docs/encounter-search-design.md` already anticipates exactly this ("recovery: index lost, corrupted, or schema changed"), so this isn't a new category of maintenance, just its first real occurrence. No defensive auto-detection/auto-rebuild is in scope - `index rebuild` stays developer-only, per `cli-mcp-parity`'s existing carve-out.
- No new CLI command or MCP tool is introduced - `cac index search`/`index_search` already exist; this only adds one optional parameter to each, kept in lockstep per `cli-mcp-parity`. No change to `mcp/server.py`'s `_TOOL_MODULES` or `tests/mcp/test_server.py`.

## Rationale

This closes the index-consistency question this campaign's body originally flagged and the prior encounter (`add-campaign-archiving`) explicitly deferred: "a subsequent encounter will update the index with the archive flag... excluded by default, but searchable as needed," per the GM's direction at the time.

Extending `_classify()` to map both the live and archive location of a campaign/encounter to the *same* row identity is the key design choice, and it's what makes this a small, contained change: `sync_write`'s existing DELETE-then-INSERT-by-identity logic already does the right thing the moment `_classify()` tells it the archived location is "the same object, now archived" rather than "an unrecognized path." That means the two archiving functions written in the prior encounter don't need to change at all - they already call `write_post` at exactly the right moment (immediately after setting `archived: true` on the frontmatter and moving the file), so the index row updates for free. Getting `_classify()`'s mapping backwards (e.g. treating the archive location as a distinct, new object rather than the same one) would instead create a duplicate row and leave the original stale - so the "same identity, `archived` differs" framing is load-bearing, not incidental.

The `sync_delete` fix is a genuine bonus, not scope creep invented for its own sake: it's the direct, mechanical consequence of the same `_classify()` change, closing a real (if narrow) latent bug from the prior encounter's read-fallback design (deleting an archived object was already possible via `_existing_campaign_path`'s fallback; only the index side of that delete was broken).

The schema-change/rebuild-required consequence is called out explicitly because silently shipping a column addition that breaks unmigrated local indexes with a raw `sqlite3.OperationalError` would be a bad experience discovered by accident rather than documented in advance - `encounter-search-design.md`'s own "recovery" framing for `index rebuild` already covers this exact situation, so this encounter is exercising a documented escape hatch, not inventing a new one.

`clean-tests-and-lint` (world-assigned) is satisfied by Verification. `cli-mcp-parity` (region) is honored: the one parameter is added to both the CLI option and the MCP tool in the same change, and no new domain/tool registration is needed since `index search`/`index_search` already exist. `console-best-practices` (region): the new `(archived)` marker is a CLI-authored literal string, not stored content, so default markup is correct, matching the precedent already set by the existing `[object_type]`/status markers on the same output line. `skills-authored-only-in-templates` is not implicated - neither `campaign-manager` nor `world-manager`'s SKILL.md currently documents `index_search`/`cac index search` at all (a pre-existing gap, not something this encounter's scope covers or should try to fix). `workflow-doc-source-of-truth` (region) applies: `docs/workflow.md`'s "Cross-cutting: priming, search, and docs" section and the "Archiving" section written in the prior encounter (which currently states "no distinction yet made between live and archived content in search results" - now false) must both be corrected in the same change.

## Plan

1. **`core/search_index.py`** - schema:
   - `_CREATE_TABLE_SQL`: add an `archived UNINDEXED` column between `updated_on` and `body`. Update `_BODY_COLUMN_INDEX` from `5` to `6` to match the shifted position.
2. **`core/search_index.py`** - `_classify`:
   - Change return type to `tuple[str, str, str, bool] | None` (adds `archived`).
   - Existing live-path branches (`WORLD_FILE_NAME`, `LORE_DIR_NAME`, `REGION_DIR_NAME`, `CAMPAIGN_DIR_NAME`, `ENCOUNTER_DIR_NAME`) all return `archived=False`.
   - Add two new branches: `len(parts) == 3 and parts[0] == ARCHIVE_DIR_NAME and parts[1] == CAMPAIGN_DIR_NAME` → `(CAMPAIGN, "", path.stem, True)`; `len(parts) == 4 and parts[0] == ARCHIVE_DIR_NAME and parts[1] == ENCOUNTER_DIR_NAME` → `(ENCOUNTER, parts[2], path.stem, True)` (the campaign name sits one level deeper than the live encounter path since it's under `archive/encounters/<campaign>/`, not `encounters/<campaign>/`).
3. **`core/search_index.py`** - `sync_write`/`sync_delete`: unpack the new 4-tuple (`object_type, campaign, stem, archived = classified`); `sync_write`'s INSERT gains the `archived` column/value; `sync_delete` ignores the unpacked `archived` (deletion is identity-keyed, unaffected).
4. **`core/search_index.py`** - `_reindex_campaigns`/`_reindex_encounters`: when building each insert's value tuple, pass `archived=False` for names sourced from `list_campaigns`/`list_encounters` and `archived=True` for names sourced from `list_archived_campaigns`/`list_archived_encounters` (distinguish by tracking which list each name came from, rather than re-deriving it after the fact).
5. **`core/search_index.py`** - `SearchHit`: add `archived: bool` field.
6. **`core/search_index.py`** - `search()`: add `include_archived: bool = False` keyword-only parameter; SELECT the new `archived` column; when `include_archived` is `False`, append `AND archived = 0` to the WHERE clause; construct each `SearchHit` with `archived=bool(row[...])`, adjusting the `excerpt`/`score` column indices for the one extra SELECTed column.
7. **`cli/index.py`**: add `--include-archived` (bool flag, default `False`) to the `search` command, threaded through to `search_index_core.search`. Update the printed result line to append `" (archived)"` when `hit.archived` is true.
8. **`mcp/index.py`**: add `include_archived: bool = False` to `index_search`, threaded through; add `"archived": hit.archived` to `_hit_to_dict`.
9. **`templates/docs/workflow.md`**: in the "Cross-cutting: priming, search, and docs" section's Search index bullet, replace the now-stale claim from the prior encounter ("no distinction yet made between live and archived content in search results") with: archived content stays indexed but is excluded from `index_search`/`cac index search` results by default; `include_archived=True`/`--include-archived` opts back in; `index_status`/`index_counts` intentionally still count archived content in its totals, without a live/archived split - flagging that asymmetry explicitly rather than leaving it to be inferred.
10. **Tests** (`tests/core/test_search_index.py`):
    - Update `test_archive_campaign_leaves_index_rows_untouched` (prior encounter): its old assertion that a default (unfiltered) search still finds the archived rows is no longer the intended contract - rewrite it to assert the row survives archiving (still present via `index_counts`) but a *default* `search()` call no longer returns it, while `search(..., include_archived=True)` does.
    - Update `test_rebuild_index_includes_archived_campaigns_and_encounters` (prior encounter) the same way: default search after rebuild excludes the archived campaign/encounter; `include_archived=True` includes them.
    - New coverage: `_classify`-level behavior verified indirectly through `sync_write`/`archive_campaign` - archiving a campaign/encounter immediately (no rebuild) flips its indexed `archived` value to `True`, verified via `include_archived=True` search returning `archived is True` and default search excluding it; deleting an already-archived campaign/encounter (via `campaign_delete`/`encounter_delete`, reachable through the existing read-fallback) removes its row from the index (fixes the latent `sync_delete` gap); a mix of live and archived hits in one `include_archived=True` result correctly reports `archived` per-hit, not uniformly.
11. **Tests** (`tests/cli/test_index.py`, `tests/mcp/test_index.py`): `cac index search --include-archived` / `index_search(include_archived=True)` includes an archived hit that a default call excludes; the CLI's printed line shows `(archived)` only for the archived hit's line.
