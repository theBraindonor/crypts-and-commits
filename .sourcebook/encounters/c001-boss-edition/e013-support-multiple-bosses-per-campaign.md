## Requirements

Change the boss/campaign relationship before the planned workflow-skills encounter: a campaign may pursue zero, one, or many bosses; a boss may have at most one current campaign assignment. The developer explicitly requested the cardinality change and authorized drafting. The lifecycle, draft-membership, prerequisite, and compatibility details below are proposed defaults for review, not separately confirmed product decisions.

1. Canonical model. Use a campaign bosses list of full canonical boss names and each boss's existing scalar campaign reference. No primary boss or implicit ordering priority. Reject malformed lists, empty elements, duplicate canonical identities (including mixed full/short spellings at input), missing targets, and conflicting ownership before writes. Stored links remain canonical; inputs accept existing bNNN/cNNN refs and legacy full names. Bossless campaigns remain supported. Multiple current bosses claiming the same campaign is healthy only when its list reciprocates exactly; a boss claimed by two non-abandoned campaigns remains an integrity error.
2. Compatibility. Read legacy campaign boss scalars as singleton lists, and missing relationship fields as empty lists, without rewriting records on reads. Reject records carrying both boss and bosses rather than choosing one silently. New relationship writes use only bosses; normalize legacy representation when a supported campaign mutation writes that record. Preserve historical names, audit creation fields, body/history, and archive locations. Keep existing single-boss promotion as a convenience interface with its current signature and retry behavior; it must work with the new model. Document older-library limitations; do not perform blanket record migration, downgrade records, or run bootstrap. Assess sourcebook schema compatibility explicitly before implementation, documenting any necessary version/upgrade decision rather than assuming bootstrap migrates data.
3. Batch selection and draft membership. Extend campaign_create(name, body, bosses=None) / cac campaign create with repeatable --boss to create the campaign and selected links atomically. Omitted/empty bosses creates a bossless campaign; existing create-name collision behavior remains. Add campaign_set_bosses(name, bosses, message) / cac campaign set-bosses NAME with repeatable --boss and required explanatory --message. This replaces the entire set only while the campaign is draft and unarchived; explicit empty list (CLI no --boss) clears it. Additions must be available, unarchived, unassigned, and eligible; retained members must have valid reciprocal state; removals release only this campaign's current assignments without changing boss readiness or body. A changed set records the reason and old/new canonical membership in the campaign Log. Repeating the same valid set is read-only, including when input order differs. Membership stays locked in open/paused/completed/abandoned/archived campaigns and after reactivation; campaign_update/body text must not bypass the relationship API.
4. Lifecycle as one commitment. Completion vanquishes every currently linked boss; reactivation returns all of them to available while retaining ownership; abandonment releases all current boss campaign links while preserving the campaign's complete historical bosses list. Archiving a completed campaign archives every currently assigned boss with it. Archiving abandoned history must not touch any released boss, whether unassigned, archived independently, or reassigned elsewhere. Existing terminal/archive/open-encounter guards and protected history/deletion rules remain. Reject deletion when a retained current/historical bosses list or reverse current claim protects campaign history. Boss design content stays frozen while assigned, and lifecycle/membership operations change only its permitted metadata.
5. Prerequisites and candidates. Preserve hard prerequisite semantics: grouping does not satisfy an unsatisfied prerequisite. If B depends on incomplete A, they cannot be selected together merely to bypass the dependency. Candidate explanations must accept healthy many-boss membership, keep assigned bosses unavailable for new selection, expose broken/missing/competing links, and reflect completion/reactivation of the whole group. No per-boss outcome, partial completion, distributed assignment, or new dependency model.
6. Atomicity and evidence. Preflight all affected campaign/boss/archive/encounter paths, references, eligibility, audit inputs, and minimum response metadata before persistence. Group creation, draft replacement, and lifecycle operations roll back the entire affected cohort on failure, including original bytes, audit fields, index rows, and fingerprint evidence; preserve unrelated records/rows and pre-existing external index divergence. Fail explicitly on incomplete recovery, never rebuild the index automatically. Exact same successful single-boss assignment retries remain read-only; a retry must never shrink a multi-boss campaign or rewrite its tactical body.
7. Prime and interface contracts. Campaign reads expose the complete bosses list. Replace singular prime context with active_bosses plus active_boss_diagnostics and active_boss_names (the canonical declared membership, including unavailable records). Empty membership gives empty collections. Healthy entries preserve metadata/name/status/archived/depends_on/campaign, summary, and budgeted body; diagnostics identify missing or inconsistent members/claims rather than masquerading as bossless. No recursive prerequisite expansion. Remove the prerelease active_boss/active_boss_diagnostic fields rather than silently selecting one member; update all affected consumers/tests and document the breaking shape change. Preserve the shared whole-response budget: all declared identifiers/state/diagnostics must fit, with explicit truncation and per-boss boss_get refs or an explicit minimum-envelope error. Ship CLI/MCP parity, literal output, short refs, body-file behavior, and registration coverage together, with logic in core and thin wrappers.
8. Documentation. Update docs/boss-edition.md to distinguish implemented one-boss behavior from this accepted-for-drafting proposal, then update its implementation boundary when shipped. Replace one-to-one assumptions in the packaged Workflow Reference Guide and document schema/library compatibility and new API/prime contracts in the same implementation change. Broader world-planner/campaign-manager skill work, branching/migration adoption guides, release numbering, and local instruction adoption remain subsequent work. No deployed-skill edits or branch-aware endpoints.

## Rationale

Several related goals can belong to one coherent tactical effort. The current scalar campaign boss field and exact-one-owner checks force a separate campaign per boss, even when one campaign should deliver them together. A many-boss campaign preserves single-campaign ownership of each goal while avoiding a privileged primary goal.

The proposed lifecycle treats completion as evidence that the entire selected goal set is achieved. Draft-only replacement makes scope adjustments explicit before execution and prevents a reopened completed campaign from quietly acquiring new goals. Historical abandoned attempts remain history, not simultaneous current assignments. Existing prerequisite semantics are intentionally preserved.
