## Requirements

Implement read-only boss candidate discovery for campaign `c001-boss-edition`, building on completed `e006-add-boss-core`. The governing design is `docs/boss-edition.md`, particularly Dependencies and precedence, Lifecycle and outcome, Agent discovery workflow, Proposed interfaces and implementation surfaces, and the accepted e001 decisions.

- Add candidate evaluation in core and matching `boss_candidates(cursor=None)` MCP / `cac boss candidates --cursor TOKEN` CLI interfaces in the same change. Keep wrappers thin, preserve structured MCP output, and use shared cursor paging. Discovery must not write records/audit metadata, create directories/indexes, change readiness, select/assign goals, or open campaigns.
- The discovery pool consists of live, unarchived, unassigned bosses in proposed or available status. Return proposed goals as not-ready explanations rather than mistaking them for eligible work. Assigned, withdrawn, vanquished, and archived bosses are excluded as selectable roots; retain archived bosses as prerequisite lookup targets. Exclude the reserved rumors namespace.
- An available pool boss is eligible only when every direct prerequisite has recorded status vanquished and no relevant integrity errors exist. Empty prerequisites are satisfied. Proposed goals remain not-ready even with satisfied prerequisites. Unsatisfied dependencies do not reset availability. Distinguish blocked available goals from proposed/not-ready goals.
- Explain unsatisfied prerequisites using full canonical names, recorded boss status/archive state, optional linked campaign name and readable campaign status, and machine-readable reason codes plus human-readable messages. Proposed/available/withdrawn prerequisites are unsatisfied; an archived vanquished prerequisite still satisfies the status rule. Paused/open/draft/abandoned linked campaigns must be visible when present. No Git merge claim follows from recorded vanquishing.
- Resolve live/archive records through shared boss storage rules. Missing references, malformed dependency lists/entries, duplicate/self edges, cycles, name/status/archive inconsistencies, ambiguous live/archive records, and broken campaign links must never produce an eligible result. Analyze graph integrity without recursion-limit failures and without silently repairing anything. Structural defects reachable from a pool boss must block that boss with actionable diagnostics; unrelated broken components must not be represented as a healthy empty store.
- Campaign inspection is read-only. When a boss carries a campaign link, expose the linked campaign status and diagnose missing/ambiguous/malformed links, reciprocal boss mismatches, and clearly inconsistent lifecycle state (for example, available linked to completed, or vanquished linked to non-completed). Do not require optional links to be present on historical/test records merely to recognize a vanquished status; do not implement assignment, coupling, new campaign fields on disk, or migration. A broken optional link, when present, is an integrity problem rather than an omitted status.
- Return a consistent page envelope with `items`, `next_cursor`, collection-wide `counts`, and explicit `diagnostics`. Candidate items carry canonical `name`, routing `summary`, recorded status, classification (eligible/blocked/not_ready), an eligibility boolean, and prerequisite/blocker explanations. Counts are computed before paging and distinguish no boss records, no selectable pool, proposed-only/not-ready goals, and a nonempty pool with all available goals blocked. Document the final field names/reason codes in the canonical guide.
- Prefer per-boss diagnostics where a canonical root can be identified. Unsafe or fundamentally ambiguous collection storage may fail the operation with an actionable domain error; never silently choose a record, skip malformed records into apparent success, or return an empty eligible list as the sole explanation. Collection-level diagnostics must be visible in CLI and MCP and prevent unsupported assertions of complete/healthy discovery.
- Order numbered canonical names `bNNN-slug` by integer boss number, then full name as a deterministic tie-break; order unnumbered names lexically after numbered names. Cover b999/b1000 and legacy permissive names. Ordering expresses reproducibility, not priority. Retain distinct full names with the same numeric prefix; do not allocate numbers, resolve short refs, or impose new numeric uniqueness rules in this encounter.
- Keep discovery bounded: summaries and explanations, never boss/campaign bodies or a recursively expanded knowledgebase. Page using shared budget helpers against the serialized/rendered candidate data rather than name lengths alone. Bound unusually large per-item and collection diagnostics/explanation lists with explicit omitted counts/truncation markers and canonical hydration references (boss_get/campaign_get); preserve identifiers, classification, eligibility, and the existence of all blockers. Truncation cannot turn blocked work into eligible work or conceal an integrity warning.
- Missing boss storage in a bootstrapped project returns an empty structured result without writes. Honor existing schema version 1, canonical name validation, archive readability, literal stored/user markdown, and branch-agnostic behavior. No current-branch lookup or integration verification. Preserve existing deployed skills and unrelated worktree changes.
- Update the packaged Workflow Reference Guide and Quickstart for the shipped discovery command, pool/classification rules, counts, diagnostics, numeric ordering, paging/truncation, and local-record limitations. Reconcile any directly conflicting design statements in the same change. Remove only candidate-discovery deferral statements that are now implemented; preserve all other deferred-feature boundaries.

Out of scope: boss_assign_campaign; campaign mutation/coupled lifecycle/deletion protection/reactivation; short-reference resolution; ID allocation or collision enforcement; rumors operations; active_boss in prime; boss indexing/stale-index handling; planning/campaign skill changes; branching or migration adoption; ranking/business-value scoring; automatic recommendations, assignment, or execution; Git/network/merge automation.

## Rationale

The boss storage and graph-editing foundation is complete, but agents cannot yet obtain a bounded explanation of which goals are ready for selection. Candidate discovery is next in the campaign sequence and provides a reusable core eligibility assessment for later promotion, without conflating planner readiness, recorded prerequisite success, or proof of integrated implementation.

Explanatory results and collection-wide counts keep an empty project distinguishable from blocked or not-ready work. Read-only integrity diagnostics are necessary because future coupling and developer repairs can leave linked, archived, or damaged records that discovery must not silently approve.
