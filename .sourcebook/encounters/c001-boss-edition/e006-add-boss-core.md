## Requirements

Implement the boss storage, planning lifecycle, and dependency foundation of `docs/boss-edition.md` for campaign `c001-boss-edition`. That document, including its accepted e001 decisions, governs this encounter.

- Store bosses as markdown/frontmatter records in the managed boss collection, with name, required routing summary (existing 500-character limit), status, archived flag, direct depends_on names, optional current campaign reference, and standard creation/update audit metadata. New bosses start proposed, unarchived, unassigned, and without dependencies. Provide a packaged body template suggesting Goal, Rationale, Success Criteria, Design Notes, and Open Questions without requiring fixed sections.
- Implement create/get/list/update, make-available, withdraw, reactivate, archive, assign-dependency, and unassign-dependency in core and expose every operation through matching CLI commands and MCP tools in the same change. Proposed interface names are boss_create/get/list/update/make_available/withdraw/reactivate/archive/assign_dependency/unassign_dependency and cac boss equivalents with hyphenated command names.
- Create requires body and summary together; update replaces body and summary together and cannot alter lifecycle, archive, campaign, name, or dependency metadata through arbitrary frontmatter. Reuse established summary validation. CLI body-taking commands support inline body, --body-file, and the existing editor fallback; MCP takes explicit body and summary arguments.
- Allow body/summary/dependency changes only for unarchived, unassigned proposed or available bosses. Changes leave an available boss available. Make-available changes proposed to available based on the planner's decision; unsatisfied prerequisites do not prevent marking a boss available. Withdraw accepts only unassigned proposed/available bosses. Reactivate accepts only unarchived withdrawn bosses and returns them to proposed. Reject other transitions, mutation of archived bosses, and mutations of linked/frozen design content. Withdrawal cannot release assignments or change campaigns.
- Standalone archive accepts only an unassigned withdrawn boss, preserves status and body, stamps its update, sets archived true, and moves it to archive/bosses. Read and canonical-name resolution work for live and archived bosses; normal list excludes archived records, with an explicit include-archived discovery option so retained allocations can be inventoried. Reject archive destination collisions and creation under a name already retained in the archive. No deletion, archive restoration, public vanquish operation, generic metadata setter, or backdoor assignment operation.
- Model all four statuses, including vanquished, and preserve optional campaign metadata for the later coupling encounter. Campaign-driven vanquishing, assignment release/reactivation, and archiving of linked vanquished bosses are deliberately deferred. Protect existing linked/vanquished records now without adding temporary public operations to manufacture those states.
- Dependencies persist full canonical boss names. Assigning dependencies rejects self references, duplicate edges, unknown targets, withdrawn targets (including archived withdrawn targets), and cycles, including indirect cycles. Resolve archived prerequisites: archived vanquished bosses remain valid prerequisites; an existing edge to a boss later withdrawn remains stored and visible. Removing an edge is explicit and never rewrites dependents automatically. Detect malformed stored dependency metadata, missing references, live/archive ambiguity, and pre-existing cycles when validating a proposed graph change; report actionable errors before writes. No candidate ranking or prerequisite-satisfaction/assignment gate is introduced here.
- Use existing permissive canonical-name validation; core does not allocate numbers or require numbered names. Accept full canonical names only in these new operations until the short-reference encounter. No rename support. Keep enumeration deterministic without presenting order as priority. Exclude the reserved bosses/rumors subdirectory from boss enumeration and reject namespace/path collisions rather than traversing outside record locations.
- A missing boss collection means an empty collection in an existing bootstrapped project. Create directories lazily; do not rewrite historical world/campaign records, create bosses from old campaigns, or require a bootstrap/migration merely to read an empty collection. Assess schema compatibility explicitly and document the result; any necessary schema change requires supported migration documentation, never implicit bootstrap migration.
- Preserve cursor paging for list and bounded body output for get consistently in CLI/MCP, literal stored markdown and user values, and structured MCP results. Endpoints remain branch-agnostic, with no Git branch checks, allocation, switching, or merge automation.
- Update the packaged Workflow Reference Guide in the same change for the shipped commands, state/lock rules, storage/archive behavior, dependencies, and boundaries of deferred work. Reconcile directly conflicting statements in the design document. Preserve existing deployed skills and unrelated user changes.

Out of scope: boss_candidates; boss_assign_campaign and all coupled campaign behavior/deletion protection; short refs/numeric allocation; rumors operations; active_boss in prime; boss search indexing or stale-index detection; world-planner/campaign-manager skill changes; branching/migration adoption guidance beyond any schema compatibility decision needed here. These remain later encounters. Do not imply those features shipped.

## Rationale

World branch settings and the prior independent work are complete. The next campaign foundation is a durable boss record with enforceable planning state and graph rules. Shipping its CLI/MCP interfaces with its core keeps the managed-content workflow usable immediately and satisfies parity. Candidate explanations and promotion can then build on tested canonical storage rather than duplicate it.

Availability expresses planner readiness rather than dependency satisfaction. Preserving that distinction, archive readability, and frozen assigned content now avoids incompatible assumptions in later eligibility and campaign-coupling work.
